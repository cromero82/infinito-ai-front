# Contexto Legal y de Responsabilidad para Diseño de Software POS ## Propósito Este documento establece los lineamientos legales, de diseño y de responsabilidad para la construcción de un sistema POS (Punto de Venta) que cumpla con la normativa colombiana mientras delega la responsabilidad de declaración al Cliente final. --- ## 1. Marco Legal y Normativo ### 1.1 Normativa Aplicable - **Resolución 000165 de 2023 de la DIAN** - Normativa principal para facturación electrónica - **Anexo 1.0** - Documento Equivalente Electrónico POS - **Anexo 1.9** - Factura Electrónica de Venta - **Estatuto Tributario - Artículo 305** - Delito de Evasión Fiscal - **Código Penal - Artículo 17** - Complicidad ### 1.2 Distinción Fundamental entre Modelos | Modelo | Descripción | Responsabilidad | |--------|-------------|-----------------| | ❌ **Software Trampa** | Diseñado para OCULTAR ventas, permite eliminar o no registrar transacciones | **Desarrollador = Cómplice** | | ✅ **Software Neutro** | Diseñado para REGISTRAR TODO, usuario decide cuándo/qué declarar | **Desarrollador = Proveedor de herramienta** | --- ## 2. Principios de Diseño que DEBES Cumplir ### 2.1 Principio de Registro Total **TODO movimiento que el usuario ingresa al sistema debe quedar registrado.** **Requisitos técnicos:** - Ninguna transacción puede ser eliminada físicamente de la base de datos - Todo cambio de estado debe quedar registrado en logs - Las ventas registradas no pueden ser modificadas en sus montos/fechas ### 2.2 Principio de Inmodificabilidad **Ningún registro de venta puede ser modificado después de creado.** **Excepción PERMITIDA:** - Solo se permite "anular" mediante un documento oficial (Nota Crédito) - La Nota Crédito TAMBIÉN queda registrada permanentemente - La anulación NO elimina la venta original, solo crea un documento compensador ### 2.3 Principio de Trazabilidad Completa **TODO lo que sucede en el sistema debe quedar registrado con:** - Fecha y hora exacta (timestamp) - Usuario que realizó la acción - Acción específica realizada - Valores antes/después (si aplica) - Hash o firma para garantizar integridad ### 2.4 Principio de Responsabilidad Clara **El usuario debe ser consciente y aceptar explícitamente su responsabilidad.** **Requisitos:** - Aviso explícito antes de usar funcionalidades "pendientes" - Confirmación de entendimiento de responsabilidad - Cláusula en licencia de uso que establece límites de responsabilidad --- ## 3. Lo que SÍ está Permitido (Diseño Legal) ### 3.1 Emisión Diferida de Documentos Electrónicos **Flujo Permitido:** ``` 1. Usuario registra VENTA COMPLETA (todos los datos DIAN) ↓ 2. Opciones: (✓) Emitir a DIAN INMEDIATAMENTE (✓) Guardar como PENDIENTE DE EMISIÓN ↓ 3. Vista con TODAS las facturas pendientes ↓ 4. Botón "EMITIR SELECCIONADOS" (fin de día/semana) ``` **Por qué es permitido:** - La venta queda REGISTRADA en logs inmodificables - El usuario solo decide CUÁNDO emitir, no SI emitir - Existe una ruta clara para emitir eventualmente - En inspección, la venta ESTÁ AHÍ (solo documento pendiente) ### 3.2 Estados Válidos para Documentos ``` VENTA_REGISTRADA (estado inicial - no editable) ↓ ┌───┴───┐ │ │ │ EMITIDA_INMEDIATAMENTE (enviada a DIAN, CUFE asignado) │ │ │ ↓ │ EMITIDA_LOTE (enviada posteriormente desde pendientes) │ PENDIENTE_DE_EMISION (usuario puede emitir cuando decida) │ ├─── EMITIDA (cuando usuario decide emitir) │ └─── ANULADA_MEDIANTE_NOTA_CREDITO (solo forma válida de cancelar) │ └─── La venta original SIGUE registrada ``` --- ## 4. Lo que NUNCA Debes Implementar ### 4.1 Funcionalidades Prohibidas Absolutamente | ❌ Prohibido | Por qué | Riesgo | |--------------|---------|--------| | Botón "Eliminar Venta" | Diseño para ocultar | **Muy Alto** | | Opción "No registrar esta venta" | Diseño para evadir | **Muy Alto** | | Permitir modificar montos/fechas después | Manipulación | **Alto** | | Permitir reiniciar numeración | Huecos en facturación | **Alto** | | Logs editables o borrables | Sin rastro de acciones | **Alto** | | "Modo DIAN" vs "Modo Real" | Doble caja por diseño | **Muy Alto** | ### 4.2 La Línea Roja que Nunca Debes Cruzar ``` ❌ CRUZAS LA LÍNEA si: - Tu sistema tiene funcionalidades diseñadas ESPECÍFICAMENTE para OCULTAR - NADA queda registrado de ciertas transacciones - El usuario puede "hacer desaparecer" ventas ✅ TE MANTIENES SEGURO si: - Tu sistema REGISTRA TODO lo que el usuario ingresa - NADA se elimina físicamente - El usuario solo decide QUÉ HACER con lo registrado - Hay logs inmodificables de TODO ``` --- ## 5. Estructura de Datos Requerida para Protección ### 5.1 Tabla Principal de Ventas (Inmodificable) ```sql -- Esta tabla NUNCA permite DELETE ni UPDATE de campos clave CREATE TABLE ventas ( id_venta BIGSERIAL PRIMARY KEY, fecha_hora_registro TIMESTAMP NOT NULL DEFAULT NOW(), fecha_hora_venta TIMESTAMP NOT NULL, usuario_id BIGINT NOT NULL, -- Datos de la venta (NO EDITABLES después de creado) monto_total DECIMAL(18,2) NOT NULL, subtotal DECIMAL(18,2) NOT NULL, iva_total DECIMAL(18,2) NOT NULL, inc_total DECIMAL(18,2) NOT NULL, -- Estado y control estado VARCHAR(50) NOT NULL DEFAULT 'PENDIENTE_DE_EMISION', -- Estados permitidos: PENDIENTE_DE_EMISION, EMITIDA, ANULADA -- Si fue emitida electrónicamente id_documento_electronico BIGINT NULL, cufe_cude VARCHAR(100) NULL, fecha_emision_dian TIMESTAMP NULL, -- Integridad del registro hash_registro VARCHAR(256) NOT NULL, -- SHA256 de los datos clave hash_anterior VARCHAR(256) NULL, -- Para cadena de bloques ligera created_at TIMESTAMP NOT NULL DEFAULT NOW(), -- NO updated_at - los campos no se actualizan, solo cambia estado mediante transacciones ); ``` ### 5.2 Tabla de Logs del Sistema (Inmodificable) ```sql -- Esta tabla registra TODO lo que sucede -- NUNCA permite DELETE ni UPDATE CREATE TABLE logs_sistema ( id_log BIGSERIAL PRIMARY KEY, fecha_hora TIMESTAMP NOT NULL DEFAULT NOW(), usuario_id BIGINT NOT NULL, -- Tipo de acción accion VARCHAR(100) NOT NULL, -- Ejemplos: -- 'VENTA_REGISTRADA', 'VENTA_EMITIDA_DIAN', 'VENTA_ANULADA', -- 'INTENTO_ELIMINACION', 'LOGIN_EXITOSO', 'CONFIGURACION_CAMBIADA' -- Detalle en JSON detalle JSONB NOT NULL, -- Ejemplo: {"id_venta": 1234, "monto": 100000, "metodo_pago": "EFECTIVO"} -- Nivel de severidad nivel VARCHAR(20) NOT NULL DEFAULT 'INFO', -- 'DEBUG', 'INFO', 'WARN', 'ERROR', 'SEGURIDAD' -- Integridad hash_log VARCHAR(256) NOT NULL, hash_anterior VARCHAR(256) NULL ); -- Índices para búsqueda rápida CREATE INDEX idx_logs_fecha ON logs_sistema(fecha_hora); CREATE INDEX idx_logs_usuario ON logs_sistema(usuario_id); CREATE INDEX idx_logs_accion ON logs_sistema(accion); ``` ### 5.3 Tabla de Transacciones de Estado (Historial) ```sql -- Cada cambio de estado de una venta genera un registro aquí -- NUNCA permite DELETE ni UPDATE CREATE TABLE venta_estado_historial ( id_historial BIGSERIAL PRIMARY KEY, venta_id BIGINT NOT NULL REFERENCES ventas(id_venta), fecha_hora TIMESTAMP NOT NULL DEFAULT NOW(), usuario_id BIGINT NOT NULL, estado_anterior VARCHAR(50) NULL, estado_nuevo VARCHAR(50) NOT NULL, motivo VARCHAR(500) NULL, -- Ejemplo: "Emisión lote fin de día", "Anulación por devolución" -- Referencia a documento si aplica id_nota_credito BIGINT NULL, id_documento_electronico BIGINT NULL, hash_registro VARCHAR(256) NOT NULL ); ``` --- ## 6. Consideraciones de Seguridad y Protección ### 8.1 Integridad de Datos **Implementar cadena de bloques ligera:** ``` Cada registro tiene: - hash_registro = SHA256(datos + nonce) - hash_anterior = hash_registro del registro anterior Esto garantiza que: 1. No se puede modificar un registro sin romper la cadena 2. Cualquier manipulación es detectable 3. Hay prueba irrefutable de cuándo se creó cada registro ``` ### 8.2 Acceso a Logs **Los logs deben ser:** - Visibles para el usuario (para su propia gestión) - No editables ni borrables - Exportables en formatos estándar (CSV, JSON, PDF) - Disponibles para autoridades cuando sea requerido ### 8.3 Roles y Permisos **Definir roles claros:** ``` ROL_CAJERO: - Puede registrar ventas - Puede emitir documentos pendientes - NO puede anular ventas (necesita supervisor) - NO puede acceder a configuraciones de sistema ROL_SUPERVISOR: - Puede todo lo del cajero - Puede generar Notas Crédito - Puede ver reportes - NO puede eliminar registros ROL_ADMIN: - Puede todo lo anterior - Puede configurar sistema - Puede gestionar usuarios - PERO TAMPOCO puede eliminar registros de ventas/logs - Todas sus acciones quedan registradas ``` --- ## 9.
